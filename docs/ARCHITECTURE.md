# Architecture contract

## Process boundaries

Manager APK → Media Service → frame transport → Camera Provider → CameraService → camera clients.

Manager owns user controls, preview and SAF import. It copies selected content into a service-owned staging area through an authenticated Binder import operation; the service validates size/type and atomically commits the import under /data/misc/vfeed. The HAL never opens arbitrary SAF URIs or source MP4 files.

Media Service is a separate privileged platform process. It owns MediaExtractor, MediaCodec, decode images, conversion/transforms, pacing and producer slots. M3 starts only after generated-camera and metadata gates pass. The Camera Provider owns camera characteristics, sessions, gralloc output buffers, request/result callbacks and a bounded request worker. It consumes normalized frames and uses a generated fallback on media loss. It never hosts MP4 extraction/playback logic.

## Binder/AIDL boundaries

Manager-to-service: permission-protected internal control API for import, select, start, stop, pause, resume, loop, resolution, fps, rotation, mirror, fit/fill and diagnostics. Status reports actual transitions and errors, never a successful state before work completes. Enforce caller identity in addition to UI permission checks.

Service-to-provider: private versioned control interface exchanges queue descriptors, immutable layout, generation, producer liveness and event notifications. If deployed across system/vendor, use stable VINTF AIDL with frozen versions and declared compatibility, or choose a placement avoiding that boundary. This custom interface is distinct from the standard camera HAL and will be designed/frozen in M4.

CameraService-to-provider: official stable AIDL ICameraProvider, ICameraDevice, ICameraDeviceSession and callback interfaces with libbinder_ndk. Use the versions generated by the pinned AOSP checkout. Handle unsupported operations using specified camera status errors. A Binder thread must not wait for decoding.

## Frame ownership

Initial transport design: three shared-memory slots containing tightly packed normalized I420 planes, plus a control protocol carrying slot index, generation, sequence, media PTS and valid byte counts. Final buffer/fence API and SELinux placement require a platform build proof before M4. Do not treat a shared address as a cross-process pointer.

Slot states: FREE → WRITING (service) → READY → READING (provider) → FREE. Producer acquires only FREE slots. Consumer receives exclusive ownership of READY slots. Publish only after the frame bytes are complete; acquire before reading. Implement synchronization through a validated IPC protocol and OS primitives with explicit ordering, not unsynchronized shared flags. Queue layout includes version, dimensions, plane offsets/strides and total size with checked arithmetic. Validate every incoming descriptor and limit allocations.

No FREE slot: drop the incoming frame and increment overflow counters. Old READY frames may be reclaimed only through an ownership transition; never overwrite READING. Consumer waits with a deadline on an event/condition, not polling. Underrun: use the deterministic fallback at the requested cadence, increment underrun counters. A session may cache its last complete frame only with its own owned copy.

At 1280x720, three I420 payloads total 4,147,200 bytes; at 1920x1080 they total 9,331,200 bytes. These exclude headers, decoder surfaces and HAL buffers. Resolution changes allocate a new generation and drain old readers before releasing old storage. Session close releases held slots, buffer imports and descriptors. Death invalidates the generation; reconnect uses a new queue and cannot reuse stale ownership tokens.

## Camera output buffer lifecycle

Framework supplies capture requests and gralloc handles, with buffer IDs and acquire fences. Cache imports by stream and buffer ID; honor cache removal and stream reconfiguration. Wait on acquire fences with a bounded timeout, map according to actual gralloc plane layout, copy/convert normalized pixels respecting row/pixel strides, unlock and return a valid release fence. I420 transport layout is not assumed to equal flexible YUV output layout.

Return each accepted output buffer exactly once, with shutter/result notifications and complete required metadata or the prescribed error notifications. Flush cancels/drains outstanding work and returns buffers; close makes the session unusable and frees resources. Bound in-flight requests by advertised maxBuffers. Do not hold provider locks across callback IPC. Test concurrent flush, requests and death explicitly.

## Timestamps and pacing

Use a monotonic capture clock compatible with the advertised SENSOR_INFO_TIMESTAMP_SOURCE. Use CLOCK_BOOTTIME if advertising REALTIME; never label an unrelated clock REALTIME. Media PTS controls selection, not the absolute sensor timestamp. Capture results and shutter for a frame use the same timestamp. Rebase media PTS on loop/seek without resetting the capture clock.

Schedule absolute deadlines from an epoch and frame index; rational fps arithmetic prevents cumulative drift. Pause/stop and restart establish a new media epoch but capture timestamps remain increasing within each session. Late decoder frames are dropped under a specified selection rule and measured. Do not burst a backlog after stalls. The HAL completes accepted requests at scheduled cadence even when the service is down.

## Camera metadata

Static metadata must match implemented stream sizes/formats, minimum durations, stall durations, fps ranges, facing, orientation, hardware level, capabilities, request/result/characteristic keys, pipeline depth and controls. Select EXTERNAL or another allowed hardware level only after its mandatory metadata is fulfilled. Do not advertise RAW, JPEG, autofocus, flash, manual sensor, reprocessing or concurrent stream support unless implemented.

M1 starts with 640x480 and 1280x720 YUV preview at 30 fps. Validate controls, default request templates, repeating empty settings reuse, frame numbers, sensor timestamps and stream combinations against the selected interface and VTS. M2 expands validated fps and dumps every characteristic. Camera1 behavior requires a later client test.

## Registration and startup

Proposed distinct instance: android.hardware.camera.provider.ICameraProvider/external/100. Confirm it is unused on the baseline image before finalizing. Proposed provider camera name: device@1.1/external/100; confirm naming rules and generated device interface version in the pinned tree. Framework-facing camera IDs are discovered from CameraManager and must not be assumed equal to the provider name.

Install a real vendor provider binary with an init rc and device VINTF fragment at M1; use format=aidl and the correct frozen provider version (version 1 on the inspected Android 13 branch). Register through AServiceManager_addService and run a Binder thread pool. Product integration adds the package and policy directories without replacing the existing Cuttlefish provider. Check framework compatibility matrices and unique device identity. Provider enumeration does not depend on Media Service startup.

Prefer eager startup for the first prototype so generated fallback exists independently. Media Service starts through platform init/service management after its data directory is available. Manager installation and permission allowlisting are separate product steps. No live init/VINTF entries are installed in M0 because no executable exists.

## SELinux domains

Expected dedicated domains: vfeed_camera_provider (HAL camera server role), vfeed_media_service (decoder and private media access), and a constrained manager app domain or platform-app placement selected by policy review. Label provider executable, service executable, service Binder names and /data/misc/vfeed storage. Separate manager/control access from HAL access; allow only authenticated descriptor exchange and required shared-memory/gralloc/codec operations.

System/vendor Binder device and service-manager selection must match the pinned transport architecture. Use applicable hal_camera attributes and platform policy patterns; do not use permissive domains or blanket allow rules. Run enforcing, collect AVC denials and validate both policy compilation and runtime. Names above are design intent, not already compiled policy.

## Failure recovery

Decoder crash/malformed or missing media: report error and provider continues fallback. Producer death: invalidate queue, release local resources and reconnect with backoff. Consumer death: service reclaims slots only after invalidating the dead generation. Camera client death: close session, return/release all resources and allow reopen. Provider death: init restarts it; CameraService clients see framework errors and may reopen after availability. CameraService restart: establish new callbacks/sessions and discard stale requests. Binder callbacks must not retain dead clients.

Counters distinguish source drops, queue overflow, underruns, output errors and restart count. Track decoded/rendered frame counts, average frame time and state transitions using bounded diagnostics. Restart tests must prove bounded memory/FD usage and no stuck ownership.
